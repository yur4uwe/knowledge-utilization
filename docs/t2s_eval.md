# Звіт оцінки системи Text-to-SPARQL

## 1. Архітектура конвеєра Text-to-SPARQL (C2)
Конвеєр автоматизованої обробки та валідації запитів реалізовано в `tests/eval_t2s.py`. Обробка кожного природномовного запиту містить 5 послідовних етапів:

1. **Генерація запиту через LLM:** Формування підказки на базі запитання та звернення до моделі (`gemini-2.5-pro`, `temperature=0.2`, `seed=42`).
2. **Синтаксичний парсер (Parser):** Валідація граматики SPARQL 1.1 через `rdflib.plugins.sparql.parser.parseQuery`. Синтаксично некоректні запити відсікаються.
3. **Верифікація за схемою (Schema Validator):** Вилучення локальних термінів (`:Class`, `:property`, `:Individual`) та їх зіставлення з еталонним словником онтології (93 локальні сутності з `data/kb.ttl`). Запити з неіснуючими термінами фіксуються як порушення схеми.
4. **Виконання у триплсторі з LIMIT (Execution Engine):** Додавання `LIMIT 50` для запобігання надмірному навантаженню та виконання через HTTP-запит до ендпойнта Fuseki (`http://localhost:3030/energy/sparql`).
5. **Порівняння з еталоном (Evaluator):** Паралельне виконання еталонного SPARQL-запиту з `tests/t2s.jsonl` та перевірка еквівалентності отриманих результуючих зв'язувань.

## 3. Класифікація та аналіз 5 помилок базової моделі (C4)

### Помилка 1 (Q03): Галюцинація назви властивості даних
- **Запитання:** *«Скільки активної потужності видає Покровська СЕС?»*
- **Згенерований запит (V1):** `SELECT ?power WHERE { :Pokrovska_Solar_SES :capacity ?power . }`
- **Клас дефекту:** Property Hallucination.
- **Причина:** Модель підставила загальну назву `:capacity` замість онтологічного предикату `:hasRatedActivePowerMW`.
- **Виправлення:** До системного промпту V2 додано список числових властивостей із зазначенням `:hasRatedActivePowerMW`.

### Помилка 2 (Q04): Галюцинація об'єктної властивості
- **Запитання:** *«Які електростанції видають потужність на ПС Вінницька 750 кВ?»*
- **Згенерований запит (V1):** `SELECT ?asset WHERE { ?asset :connectedToSubstation :Substation_Vinnytska_750kV . }`
- **Клас дефекту:** Relation Hallucination.
- **Причина:** Модель використала довільну назву `:connectedToSubstation` замість стандартного IEC CIM зв'язку `:suppliesPowerTo`.
- **Виправлення:** У промпті V2 явно визначено допустимі предикати зв'язку між генерацією та підстанціями.

### Помилка 3 (Q05): Невідповідність імені класу
- **Запитання:** *«Знайди всі гідроелектростанції або накопичувачі та їхню потужність»*
- **Згенерований запит (V1):** `SELECT ?asset ?power WHERE { ?asset a :HydroStation ; :hasRatedActivePowerMW ?power . }`
- **Клас дефекту:** Class Mismatch.
- **Причина:** Скорочення назви класу `:HydroPowerPlant` до `:HydroStation`.
- **Виправлення:** Включення повної таксономії класів генерації в контекст підказки.

### Помилка 4 (Q09): Лексична неточність у назві сутності
- **Запитання:** *«Яка сумарна потужність сонячної генерації в енергосистемі?»*
- **Згенерований запит (V1):** `SELECT (SUM(?power) AS ?total) WHERE { ?ses a :SolarPlant ; :hasRatedActivePowerMW ?power . }`
- **Клас дефекту:** Out-of-Vocabulary Class.
- **Причина:** Вживання терміна `:SolarPlant` замість зафіксованого в онтології `:SolarPowerPlant`.
- **Виправлення:** Чітке перерахування класів відновлюваної генерації в описі схеми.

### Помилка 5 (Q11): Комплексна галюцинація схеми
- **Запитання:** *«Які споживачі мають напругу 110 кВ і потужність понад 100 МВт?»*
- **Згенерований запит (V1):** `SELECT ?consumer ?power WHERE { ?consumer a :Consumer ; :voltage 110.0 ; :power ?power . FILTER (?power > 100.0) }`
- **Клас дефекту:** Multiple Vocabulary Fabrication.
- **Причина:** Одночасне вигадування неіснуючих класів і властивостей (`:Consumer`, `:voltage`, `:power`).
- **Виправлення:** Запровадження жорсткого правила заборони використання термінів за межами наданої схеми та надання прикладу типізації `:EnergyConsumer` з `:hasVoltageLevelKV`.
